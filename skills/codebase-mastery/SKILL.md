# Codebase Mastery

基于三层递进认知框架和六步实战法，系统性掌握新代码库。

## 认知框架：三层递进

```
是什么(What) → 怎么实现(How) → 为什么这样设计(Why)
```

先建立全景图，再深入局部。禁止在未完成 What 层之前直接读源码。

## 六步实战法

### Step 1: 先跑起来，建立体感

> "没跑过的代码不属于你"

执行顺序：

1. 编译通过 → 理解依赖关系和构建链路
2. 跑通最小 demo → 确认环境 OK，建立信心
3. 跑单元测试 → 测试即文档，看哪些模块有测试
4. 故意改坏一个地方 → 观察报错，理解模块边界

### Step 2: 画三张图，强制输出

| 图 | 画什么 | 检验标准 |
|---|--------|---------|
| 架构图 | 模块划分 + 数据流向 | 能给外人讲清楚系统全貌 |
| 调用链图 | 一个完整请求从入口到出口的调用栈 | 能默写出核心路径 |
| 状态机图 | 关键实体的生命周期和状态转换 | 能说清每个状态变化的触发条件 |

手画在纸上，画不出来说明没懂。

### Step 3: 追踪一条完整数据流

选一个最核心的场景，从入口追到出口，不放过任何一行。用断点调试或日志追踪，在每个关键节点打 log，观察实际数据长什么样。

### Step 4: 改一个需求，逼自己动手

> "看懂"和"能改"之间隔着一条鸿沟

由易到难：

| 难度 | 练习 |
|-----|------|
| ⭐ | 加一行日志，打印关键变量 |
| ⭐⭐ | 修改一个配置项，观察行为变化 |
| ⭐⭐⭐ | 修复一个简单 bug |
| ⭐⭐⭐⭐ | 新增一个监控指标 |
| ⭐⭐⭐⭐⭐ | 实现一个小功能 |

### Step 5: 写下来，教别人

费曼学习法：如果不能用简单的话解释清楚，说明还没真正理解。

输出形式：给同事讲 15 分钟 / 写技术博客 / 画一页纸架构图 / 写代码注释

### Step 6: 对比思考，理解设计决策

每个设计选择背后都有 trade-off，理解"为什么不"比理解"是什么"更深刻。对每个关键设计追问：为什么选 A 而不选 B？各自的 trade-off 是什么？

## 避坑指南

| 坑 | 正确做法 |
|---|---------|
| 从第一行代码开始顺序读 | 先读入口和出口，再读中间 |
| 试图一次读懂所有模块 | 一次只追一条数据流 |
| 只看代码不运行 | 边看边跑，验证理解 |
| 跳过测试代码 | 测试是最好的使用文档 |
| 只看不写 | 至少改一行代码，打破心理门槛 |
| 迷失在第三方库代码里 | 先假设第三方库是黑盒，理解接口即可 |

## 执行工作流

当用户请求学习某个代码库时，按以下流程执行：

1. **探索代码库结构** — 读取 README、目录结构、构建文件、配置文件，建立全局认知
2. **构建 What 层** — 总结项目定位、解决什么问题、核心场景、微服务组成、对外能力
3. **构建 How 层** — 追踪核心数据流，提炼关键机制实现方式（参考 [how-layer-guide.md](references/how-layer-guide.md)）
4. **构建 Why 层** — 对每个关键设计决策做对比分析，解释 trade-off（参考 [why-layer-guide.md](references/why-layer-guide.md)）
5. **生成学习规划** — 基于代码库规模和复杂度，输出分阶段学习计划
6. **提供实战建议** — 针对具体代码库给出可操作的练习任务

## 核心原则

读 3 遍不如跑 1 遍，看 10 遍不如改 1 行。
